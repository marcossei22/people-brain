## 2. O seletor de persona é **"quem eu sou"**

É de quem são os olhos. Não "quem estou avaliando".

São dois eixos independentes, e é justamente a separação deles que carrega a tese:

```
quem OLHA   →  seletor no topo        →  Viewer { pessoaId, papel }
quem é OLHADO →  a URL /brain/pessoa/[id]  →  o alvo
```

O seletor troca só o primeiro. Com ele em **Marina** e a URL em `/brain/pessoa/carla`, é a gestora vendo o dossiê da report. Trocando o seletor pra **Carla** — sem sair da página — é a Carla vendo o próprio dossiê. Mesma tela, mesmo componente, campos gated por `permissoes.ts`.

Esse é o momento do vídeo. Se fossem duas telas diferentes, "sem arquivo secreto" seria promessa. Sendo uma só, vira fato que dá pra apontar na câmera.

As três personas e o que cada uma prova:

| Ver como | `papel` | Prova |
|---|---|---|
| Marina Duarte · Eng Manager | `gestor` | O loop de atenção e a estrela |
| Carla Nunes · Eng | `colaborador` | Sem arquivo secreto — e as affordances de contestar/adicionar contexto |
| Helena Prado · CHRO | `chro` | Diagnóstico de organização, escopo **agregado** |

E o eixo "quem eu sou" é o que ativa a recusa de acesso: com a Marina no seletor, abrir a Letícia (que não é report dela) bate em `podeConsultar` e devolve *"Pares não consultam o registro de pares"*. Não é login. É um seletor exposto de propósito, que também serve de orientação pro avaliador entender de que ângulo está olhando.

## Design Thinking

Before coding, understand the context and commit to a BOLD aesthetic direction:
- **Purpose**: What problem does this interface solve? Who uses it?
- **Tone**: Pick an extreme: brutally minimal, maximalist chaos, retro-futuristic, organic/natural, luxury/refined, playful/toy-like, editorial/magazine, brutalist/raw, art deco/geometric, soft/pastel, industrial/utilitarian, etc. There are so many flavors to choose from. Use these for inspiration but design one that is true to the aesthetic direction.
- **Constraints**: Technical requirements (framework, performance, accessibility).
- **Differentiation**: What makes this UNFORGETTABLE? What's the one thing someone will remember?

**CRITICAL**: Choose a clear conceptual direction and execute it with precision. Bold maximalism and refined minimalism both work - the key is intentionality, not intensity.

Then implement working code (HTML/CSS/JS, React, Vue, etc.) that is:
- Production-grade and functional
- Visually striking and memorable
- Cohesive with a clear aesthetic point-of-view
- Meticulously refined in every detail

## Frontend Aesthetics Guidelines

Focus on:
- **Typography**: Choose fonts that are beautiful, unique, and interesting. Avoid generic fonts like Arial and Inter; opt instead for distinctive choices that elevate the frontend's aesthetics; unexpected, characterful font choices. Pair a distinctive display font with a refined body font.
- **Color & Theme**: Commit to a cohesive aesthetic. Use CSS variables for consistency. Dominant colors with sharp accents outperform timid, evenly-distributed palettes.
- **Motion**: Use animations for effects and micro-interactions. Prioritize CSS-only solutions for HTML. Use Motion library for React when available. Focus on high-impact moments: one well-orchestrated page load with staggered reveals (animation-delay) creates more delight than scattered micro-interactions. Use scroll-triggering and hover states that surprise.
- **Spatial Composition**: Unexpected layouts. Asymmetry. Overlap. Diagonal flow. Grid-breaking elements. Generous negative space OR controlled density.
- **Backgrounds & Visual Details**: Create atmosphere and depth rather than defaulting to solid colors. Add contextual effects and textures that match the overall aesthetic. Apply creative forms like gradient meshes, noise textures, geometric patterns, layered transparencies, dramatic shadows, decorative borders, custom cursors, and grain overlays.

NEVER use generic AI-generated aesthetics like overused font families (Inter, Roboto, Arial, system fonts), cliched color schemes (particularly purple gradients on white backgrounds), predictable layouts and component patterns, and cookie-cutter design that lacks context-specific character.

**Registro editorial**, não dashboard. Papel quente com grão em vez de branco clínico; Fraunces no display, Newsreader na prosa do registro, Instrument Sans na navegação, IBM Plex Mono nas evidências. Um acento só — ocre, reservado ao reconhecimento.

## Sobre os documentos

O princípio que eu usaria pra organizar: **agrupar pela pergunta que cada documento responde**, não pelo formato do arquivo. Formato é detalhe de implementação; a pergunta é o que faz alguém saber onde procurar — e, mais importante, é o que deixa explícito *por que o Brain tem o direito de dizer qualquer coisa sobre alguém*. Sem esses documentos ele é um LLM com opinião.

### Cinco tipos

| Documento | Pergunta que responde | Formato | O que o Brain faz com ele |
|---|---|---|---|
| **Régua de carreira** | O que esperamos em cada nível | Estruturado: trilha × nível × comportamento observável | Compara evidência contra expectativa. É o único que produz veredito |
| **Cultura e tom** | Como a gente fala | Prosa | Governa **como** se diz. Nunca se a pessoa é boa |
| **Contexto do ciclo** | O que importa agora | Prosa curta, **com validade** | Pondera o que conta como impacto neste semestre |
| **Política de decisão** | Quando e quem decide | Regras | Sabe que dinheiro é anual e promoção é quando estiver pronta; sabe o que o comitê precisa ver |
| **Procedimentos** | Como o Brain trabalha | Markdown executável | Um por tarefa: preparar 1:1, montar caso de promoção, rascunhar feedback |

Os quatro primeiros são **conteúdo** — o que a empresa acredita. O quinto é **procedimento** — como o Brain opera. São naturezas diferentes e eu separaria visualmente, porque a promessa "você pode ler e mudar como isso funciona" só fica de pé se o procedimento estiver visível como documento, não escondido em código.

### O campo que faz a página valer

Cada documento carrega, na própria ficha, **o que o Brain faz com ele** — e o que ele *não* faz. O de cultura diz, na cara: *"usado só para tom. Não é critério de avaliação."*

Sem esse campo isso é um wiki. Com ele, a página responde antecipadamente à pergunta que a liderança vai fazer — "então a IA me avalia contra os valores?" — e a resposta está escrita no próprio documento, não numa fala de vídeo.

### Como os documentos entram

Três modos, e o terceiro é o que interessa:

1. **Escrever no produto** — editor simples, pra cultura e contexto
2. **Subir arquivo** — a empresa já tem um ladder em PDF ou Doc; ele entra e vira régua estruturada
3. **Derivar da evidência** — o Brain propõe, o humano aprova

O modo 3 não é exclusivo da régua, e acho que é aí que a coisa fica boa. Ele generaliza: *"seu documento de cultura fala em 'ownership'. ## O que é

Framework da Vercel para agentes duráveis, **filesystem-first**. v0.29.4, Apache 2.0, 4.2k estrelas, último push ontem. A estrutura é a interface de autoria:

```
agent/
  agent.ts          modelo e config
  instructions.md   system prompt sempre ativo
  tools/*.ts        funções tipadas que o modelo chama
  skills/*.md       procedimentos carregados sob demanda
  channels/*.ts     HTTP, Slack, Discord
```

## O alinhamento com a nossa arquitetura é quase constrangedor

As decisões **#19** e **#20** — que eu tinha errado na primeira versão e você me corrigiu — são o modelo nativo do Eve, palavra por palavra:

> *"Loading a skill adds instructions, never a new execution surface. If you need typed runtime behavior, reach for a tool instead."*

É a §6.5 da nossa ARQUITETURA. `load_skill` puxa o markdown pro contexto quando a descrição casa com o pedido; a tool continua sendo só acesso. Nossas sete skills viram sete arquivos em `agent/skills/`, e "abre a pasta" passa a ser a resposta pra *"como isso funcionaria de verdade?"*.

## E ele resolve o nosso problema mais difícil

A decisão **#21** — permissão em código, nunca em prompt. O Eve tem duas formas de passar contexto, e uma delas é armadilha:

| Caminho | Onde roda | Serve pra permissão? |
|---|---|---|
| `clientContext` no `send()` | Vira **mensagem de usuário** no prompt | **Não.** É contornável ao vivo |
| `AuthFn` em `channels/eve.ts` | Camada de canal, **antes de qualquer chamada ao modelo** | **Sim** |

O `AuthFn` recebe o `Request` cru e devolve um `principalId`. Dentro da tool, `ctx.session.auth.current.principalId` é o viewer — e o modelo não tem como forjar, porque a resolução aconteceu antes dele existir no turno. Nosso seletor de persona manda um header, o `AuthFn` traduz pra pessoa, e `permissoes.ts` continua sendo a única fonte de verdade.

Isso é *melhor* do que eu conseguiria improvisando permissão numa rota de AI SDK.

## Integração com Next

`withEve(nextConfig)` — um dev server, um deploy na Vercel, rotas same-origin, sem CORS. No cliente, `useEveAgent()` devolve `data.messages` no formato `UIMessage` do AI SDK, mais `status`, `events`, `send`, `stop`, `reset`. Tool calls e resultados chegam como partes da mensagem, o que entrega de graça os dois itens do §7: o **contrato de render** (a tool devolve `{tipo, payload}`, a gente escolhe o componente registrado) e as **tool calls visíveis** do §7.2.

Infra: **nenhum banco**. Local grava em `.eve/.workflow-data`; na Vercel usa Vercel Workflow. E o sandbox — que a decisão #16 recusa — é dispensável: skills estáticas não precisam dele, e `disableTool()` remove `bash`, `read_file`, `write_file`, `glob`, `grep` e `web_fetch`. O agente fica sem superfície de execução, exatamente como especificamos.

# Handover — kick off a fresh analysis session

Create a **handover chip** (via the `spawn_task` tool) that, when the user clicks it, spins off a NEW
self-contained session to KICK OFF analysis of a topic. The spawned agent must, in order: (1) read the
relevant context read-only, (2) send the user a concise summary, (3) ask the necessary clarifying
questions — and **NOT** start coding or writing a PRD until the user answers.

This is a hand-off, not the work itself. The point is a clean kickoff: understand → summarize → ask.

## Steps

### 1. Determine the topic & scope
From the skill args or the current conversation (e.g. "Tema 2", "the auth refactor", "the flaky test").
If it's genuinely ambiguous, ask the user ONE short question. Don't over-ask — usually the topic is
obvious from what was just discussed ("the next theme", "this bug").

### 2. Gather concrete context pointers
List the exact files/docs the spawned agent should read — real paths, not vague areas. The spawned
session has **no memory of this conversation**, so the chip prompt is its only briefing (plus the
project's CLAUDE.md / auto-memory). For this project (Workr) that usually means:
- the relevant `docs/research/*` (status/backlog, research notes) and `docs/prd/*`,
- the specific `app/src/...` / `app/src-tauri/...` code the topic touches,
- a one-line statement of where the topic sits in the roadmap / what was just finished.

### 3. Call `spawn_task`
- **`title`** — imperative, < 60 chars (e.g. "Kick off Tema 2 analysis").
- **`prompt`** — SELF-CONTAINED. It must:
  1. List the exact context to read, **read-only — do NOT code**.
